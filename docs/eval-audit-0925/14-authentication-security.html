Technical Requirements

14. Authentication Security

✅ PASS

The repository supports a "Yes". · audited 2026-09-25 · origin/main @ 9881704

E-mail and password signup and login go through better-auth. Passwords are hashed with scrypt and a random salt per user, stored as salt:hash in accounts.password. Password reset e-mails are now actually sent (they go to Mailpit). The question itself passes, but there is a data-exposure bug next to it that an evaluator can find in the Network tab.

What the evaluator is asked

Does the user management system provide secure authentication?

  • Email and password signup/login
  • Properly hashed and salted passwords
  • Ask the team to explain their password security implementation.

Red flags

highAny logged-in user can download every user's e-mail address

users.getUsers and users.searchUsers (apps/backend/src/users/users.router.ts:94–107) use ProtectedMiddleware (any logged-in user) instead of AdminMiddleware, and return the full users row. Verified today: logged in as didi@example.com (a normal user), GET /api/trpc/users.getUsers returned the admin's and every other user's e-mail, role, ban status and 2FA flag. Only the admin dashboard calls getUsers, and nothing in the frontend calls searchUsers. Suggested fix: change both decorators to @UseMiddlewares(AdminMiddleware). It is a two-line change.

lowReset link is written to the backend log

auth.instance.ts:69 logs the full reset URL. Anyone who can read the container logs can reset that account. Remove the line or log only the e-mail.

lowchangePassword input typed as any

The Zod schema still validates the input, but @Input() input: any (users.router.ts:67) looks careless if someone opens the file.

What the code shows

curl -sk -c jar -d '{"email":"didi@example.com","password":"Qwerty123!"}' …/api/auth/sign-in/email   → 200
curl -sk -b jar …/api/trpc/users.getUsers
{"result":{"data":{"json":[{"id":"e912…","email":"admin.eventra@gmail.com","role":"admin",
  "banned":false,"twoFactorEnabled":false, …},{"email":"didi@example.com", …

Fix before the evaluation

  1. Change getUsers and searchUsers to AdminMiddleware and add a router test that a normal user gets FORBIDDEN (15 min).
  2. Remove the reset-URL log line.

In the room: what to show and say

"better-auth hashes with scrypt, N=16384, r=16, p=1, 64-byte key, and a random 16-byte salt per password. The hash is in accounts, never in users."
