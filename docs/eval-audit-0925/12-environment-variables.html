12. Environment Variables

⚠️ AT RISK

Depends on a fix or on how strict the evaluator is. · audited 2026-09-25 · origin/main @ 9881704

.env is git-ignored and .env.example exists. The TLS private key is no longer tracked (Caddy issues its own certificate). What remains is tracked default values: apps/backend/.env.development and docker-compose.yml contain a placeholder auth secret, the database password transcendence and the three demo-account passwords. They are labelled as demo values, but the sheet says any credentials outside .env mean "immediate project failure", so this depends on how strict the evaluator is.

What the evaluator is asked

Are credentials properly secured?

  • .env file exists and is in .gitignore
  • .env.example file is provided
  • No sensitive credentials in the repository
  • Any credentials, API keys, or sensitive information found in the repository (outside of .env) will result in immediate project failure.

Red flags

highDemo passwords and DB password are in tracked files

apps/backend/.env.development: BETTER_AUTH_SECRET=dev-only-insecure-secret-change-in-production, SEED_ADMIN_PASSWORD=Transcendence123! and others. docker-compose.yml uses the same values as ${VAR:-default} fallbacks. README §9 prints the demo passwords in a table. None of them is a real secret, but the team has to be ready to argue it.

lowOld key is still in git history

caddy/certs/local-key.pem was tracked from 90126c2 to 61b149d. It was a local mkcert key, but git log --all -- caddy/certs/ shows it. Rewriting history this close to the evaluation is riskier than leaving it. Know the answer if asked.

What the code shows

git ls-files | grep -E "\.env|\.pem"
.env.example
apps/backend/.env.development

Fix before the evaluation

  1. Rehearse the argument: "These are localhost demo values so the stack starts with one command. The file header says so. Production values go in .env, which is ignored."
  2. If you want to remove the risk (30 min): make the seed passwords and the auth secret come only from .env, and have docker compose up fail with a clear message when .env is missing. The cost is one extra step (cp .env.example .env) in the demo. Talk it over as a team. It trades a strictness risk for a "single command" risk.

In the room: what to show and say

Open .gitignore, .env.example, and the header comment of .env.development.
